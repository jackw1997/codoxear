Agent switching and local storage

The web client connects directly to independently deployed Hubs. Each Hub owns sign-in, membership, Computer permissions and its own accounts. Computers make outbound connections to their Hub and own execution, files and runtime state. The client keeps one conversation workspace mounted while you switch agents across authorized Computers and Hubs.

Sign-in and access

Add a Hub by its URL, then sign in through its configured Google or Feishu application. Multiple signed-in identities can remain active for the same Hub. The client displays the union of their authorized resources and submits each action once through a suitable individual identity. Accounts are not merged by name or email.

Owners and admins can see all Computers for administration. Using a Computer, including agent creation, requires an explicit Computer allowlist grant for every person. File access is separately limited to approved workspace grants. A cached conversation never grants execution or file access.

Switching, disconnection and revocation

Selection checks current access before showing a cached preview. Switching cancels the previous conversation stream and pending message requests. Stale responses cannot overwrite the selected conversation. Directory updates remove inaccessible resources and invalidate affected previews. Hub and Computer checks remain authoritative for every protected action.

Removing a Hub identity disconnects that identity from the client; it does not delete the person's Hub account. A closed or offline client learns about revocation at its next authenticated interaction. Saved conversation history is independent of the lifetime of a local agent process.

Deployment

The frontend, Hub and Computer are separate packages. The frontend needs no backend files or central account gateway to run. Computer service installation, pairing and startup happen on the Computer; the web interface creates its pairing code and manages its user allowlist.
