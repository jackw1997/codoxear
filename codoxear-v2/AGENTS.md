# v2 scope and requirement precedence

The current conversation takes precedence over historical implementation prescriptions. Read [docs/requirements-reconciliation.md](docs/requirements-reconciliation.md) when deciding whether an older design statement is still a requirement. This file applies only to `codoxear-v2/`; it does not change the legacy application or its deployment.

- Computer backend, Hub backend, native PTY/broker implementation and new test/verification tools use TypeScript. Retained frontend JavaScript and ordinary Node build/bootstrap scripts are permitted. Do not add Python or import, read, copy at build time, or execute the original `codoxear/` application as a v2 dependency. Assets already owned by v2 stay self-contained.
- For new managed sessions, use OAR behind a thin Codoxear runtime interface on the Computer, with explicit native extensions for required capabilities OAR cannot honor. Existing terminal sessions retain native detached Node PTYs and private broker sockets; do not adopt arbitrary running CLIs by PID or silently restart them. A loopback Python runtime adapter does not satisfy the native-runtime requirement. External installed Codex, Pi and Claude Code CLIs, Git and configured media executables are allowed interfaces. See R45 for the accepted refactor direction and preservation requirements.
- Preserve independently runnable Computer → Hub ← Client boundaries. A Computer has one active Hub binding and owns execution, native logs, files/Git and authorized remote work. Each independent Hub owns its accounts, database, signing key, membership and permissions. Client presentation does not require a server gateway or mandatory global identity service. Explicit optional shared-authority compatibility may remain; it must not become an independent-Hub dependency.
- Same-Hub cross-Computer subagent creation is the current delegation scope: route Computer A → its Hub → Computer B and enforce the initiating principal's delegated target creation authority. OAR is a local runtime adapter, not the network or authorization layer. Same-Hub membership alone is not a grant to execute on every Computer. Cross-Hub subagent delegation is explicitly deferred to later versions: the current tool resolves target Computers only within the initiating Hub and rejects cross-Hub targets. Do not implement federation or cross-Hub delegation grants in this iteration. This scope decision does not remove existing multi-Hub client or Computer-transfer functions. See R43–R44 in the reconciliation record; same-Hub Pi parent/child delegation was accepted through the public interface on 7 October 2026; Codex/Claude parent-tool registration remains separate.
- Keep the agent sidebar and conversation workspace primary, with Hub/Computer placement secondary. Preserve existing v2 functions, three theme families, root design invariants, store/widget ownership and explicit transcript replacement rules. RAFT-inspired creation offers the same Pi/Codex/Claude runtime choices, provider URL, API key, model/custom model and relevant launch settings.
- Creation shows actual provider, model and reasoning selections read from configuration. Do not offer “Configured on computer”, “Configured default” or hidden runtime-default selections. Unknown values require an explicit choice. Named providers come from the Computer configuration; Custom API remains available for new endpoints. A submitted selection is explicit and must be honored or rejected clearly.
- Dependencies, priority and snooze are conversation organization metadata. Preserving them does not authorize adding an execution scheduler. The accepted durable remote queue is separate from terminal-local queue unification.
- Preserve the user's existing Kimi/LiteLLM endpoint, key and model and public Hub/client addresses. R47 authorizes fresh accounts, catalogs and Computer identities; preserve old catalogs and histories in the separate private archive without importing them into the fresh deployment. Earlier topology/restoration requirements are superseded. The R41 scoped stop authorization applies to owned demo/test containers. Preserve unrelated host sessions and the legacy application. Reject unsafe PID-only relay imports; use proven runtime incarnation identities.
- Linux is the accepted native migration target. macOS secure workspace support and real-device/mobile-platform acceptance remain pending until separately verified. A phone viewport does not establish Safari, HarmonyOS, iOS or Android acceptance.

The root [AGENTS.md](../AGENTS.md) remains binding for testing and product behavior:

- All behavioral verification of server, broker, PTY, sessions, browser and related runtime work runs in Docker. A throwaway host `HOME` is not isolation. Never test the production listener at `127.0.0.1:8743`.
- Never clean up by process patterns (`pkill -f`, `killall`, broad `pgrep | xargs kill`). Prefer owned container teardown. If a non-session host process is explicitly started, record and clean up its exact PID only.
- Treat the development computer as an 8 GiB target. Run verification through the shared per-user lock; serialize test files and cap verification containers at 2 GiB. This ceiling is a starting constraint, not evidence that the entire suite fits. Do not create overlapping preview stacks. Record total process-tree/cgroup memory before increasing concurrency. Saved conversation history must not imply an indefinitely resident backend process.
- The user's 6 October request authorizes stopping all Codoxear demo/test containers created during this work, including resumed copies. Preserve their data, credentials and histories; this scoped cleanup supersedes the earlier instruction to preserve running agents inside those containers. It does not authorize terminating unrelated host sessions.
- No raw source-string tests. Execute behavior and assert outcomes; CSS checks parse rules. Import-graph/build checks are architectural checks, not behavioral acceptance.

## Frontend and backend source boundary

- Web frontend source is in `frontend/web/`; HarmonyOS source is in `frontend/harmonyos/`.
- The web frontend owns `frontend/package.json` and `frontend/package-lock.json`. Install and build it independently from `frontend/` with `npm ci` and `npm run build`; serve it there with `npm start`.
- Root `package.json` is the development/verification coordinator. Deployable backend packages are exported with `scripts/package-component.ts`: Computer, Hub, optional Identity and optional compatibility Server each own a manifest, lockfile, entry points and explicit shared-library closure in `components/<role>/`. Each exported package installs and builds independently with `npm ci && npm run build`. Root `npm run build` coordinates development builds only.
- Components must not import another component implementation, including through a shared library. Shared libraries have no upward imports into services. Architecture checks enforce the complete import closure and published packages contain only that closure.
- Backend APIs run without frontend files. Browser pages require the separately built immutable frontend bundle via absolute `CODOXEAR_FRONTEND_ASSETS_ROOT` or `frontendAssetsRoot`; no implicit repository paths. Production images contain only their own runtime. The ephemeral provisioning/verification tool image is not a resident service.
- The browser communicates with backend services through public API protocols and frontend-owned DTOs. Frontend code must not import backend implementation from root `src/`.
- Separate packages and successful builds establish package/build separation only; do not describe frontend/backend behavioral isolation as proven until current Docker behavioral evidence is recorded.
- Exercise the real interface before claiming a user-facing feature works. Report implemented slices, native/browser evidence, missing acceptance and external blockers separately. Record every requested task's resolution or explicit deferral.
- Keep one authoritative writer per displayed value; retain widget-owned subscriptions, atomic stores, producer-backed model/effort/runtime state, scoped caches and stale-response fencing. Escape does not close/cancel a dialog. Downloads must preserve the mounted application and follow its teardown contract.
- Preserve root appearance tokens, family-invariant fonts, 44px touch targets, undimmed bounded overlays, and the locked touch/desktop session-card branches. Apply semantic design rules, not legacy file locations.
- Do not commit secrets or private runtime state. Deliver reviewed committed snapshots; keep configuration and credentials external. Preserve running agents during changes.

Root instructions about `codoxear/util.py`, Python module locations, `pip install`, `pipx`, `scripts/deploy.sh`, the global password gate and restarting `codoxear-server.service` describe the legacy product. They do not prescribe v2 implementation or authorize using the legacy deploy command for v2. Use the v2 entry points and isolated verification configuration. This clarification preserves the root Docker, safety, design and behavioral-testing rules.

## Provider-only client identity (7 October 2026)

- Google and Feishu are the only registration/sign-in providers. No password, email-code or SMS login endpoints or migration fallback. The owner explicitly waived account migration.
- R54 removes client device signing keys. Use ordinary revocable Hub OAuth/refresh sessions, scoped to each independently verified identity and Hub. A client profile/email is not authentication.
- R54 initializes ownership through a private, expiring, single-use URL carried through provider sign-in. Its first successful allowed provider callback atomically assigns ownership and consumes initialization. No separate setup-code form and no ownership for the first public visitor.
- Provider app secrets remain in private backend configuration. Actual provider login acceptance requires configured real apps; controlled-provider browser tests are reported separately.

## Hub-owned provider authentication and simultaneous identities (R52–R53)

- R52 supersedes the unshipped R51 global login-broker design. Each independent Hub owns provider OAuth, local accounts, signing keys and permissions. The static client discovers that Hub's advertised providers; it does not require a global account/login service.
- One Hub represents one organization. Configure at most one Feishu application and one verified tenant on that Hub. Other organizations deploy their own Hubs/apps. Optional Google identities are subject to that Hub's explicit access policy. App secrets remain in private Hub configuration.
- R53 supersedes the exclusive acting-account interpretation in R52. All saved identities for a Hub contribute access simultaneously. Present the union of authorized resources without duplicate Computers/agents; dispatch each operation once using a valid individual identity that actually grants its required capability. Do not merge identities by email/name, manufacture ownership, or combine partial proofs into a synthetic principal. Ordinary login sessions and credential vault entries remain Hub/account scoped.
- The Hub owner chooses allowed sign-in types: Feishu only, Google only, or both with room for configured future providers. Enforce the policy on new sign-ins and existing sessions and tokens. Retain a policy-blocked local identity so it can recover when the owner allows that provider again.
- R54 initialization links replace the earlier separate deployment-code form. No passwords, verification-code delivery, account migration or first-public-visitor ownership are introduced.

## R54 — Initialization links, Hub roles and explicit Computer allowlists

- The client starts with an Add Hub URL field, without preconfigured Hub suggestions. After discovery, enabled provider sign-ins are parallel, separate choices. All signed identities remain active; deduplicate shared resources without merging accounts by email/name.
- Deployment generates a private expiring initialization URL. A verified identity from any enabled provider can become Owner through it. Configured Feishu must not force a Google owner to use Feishu. Later ordinary client login recognizes that same verified identity as Owner.
- Owner, Admin and Member are Hub administration roles, displayed beside identities. Owners promote/demote admins and remove admins/members. Admins invite/remove ordinary members but cannot remove or demote admins/owner. Provider policy remains owner-controlled.
- Owners/admins see all Computers and manage their allowlists. Members see only Computers explicitly allowing one of their signed-in identities. Every human, including the Hub owner/admin and Computer owner, must be explicitly allowlisted to use a Computer or create/use its agents. Creating or owning a Computer grants no automatic execution access. Agent sharing/retained rights must not bypass the Computer allowlist.
- Computer service authentication and outbound WSS binding are separate from human sign-in. Retain those service credentials; removing client device signing keys does not remove Computer authentication. Hub authority enforces allowlists for execution, streams, files, queues and delegation.
- Public sign-in without Hub membership is a signed-in nonmember state with an invitation action, not an unexplained Hub access error or automatic membership. Existing unrelated sessions and LiteLLM settings remain preserved.

## Customer acceptance through the browser

- Before handing a feature back for user verification, exercise the real web pages as a customer and inspect screenshots. Cover Owner initialization, second-identity sign-in and invitation acceptance, two Computers with separate allowlists, permitted agent creation, read-only access and revocation. Click Files, Details and Unattended mode on managed sessions; a successful chat alone does not establish toolbar support.
- Create accounts, invitations, Computer records, allowlists and agents through the UI in this acceptance journey. Direct API mutations, credential injection and backend-seeded grants do not count as browser acceptance. Computer service installation/attachment and controlled provider/driver fixtures are separate infrastructure boundaries and must be disclosed; do not describe them as browser-only deployment or real provider/model acceptance.
- Show screenshots of the requested journey before claiming readiness. Mask pairing codes, invitation codes, credentials and private runtime state. Keep verification Docker-isolated and bounded by the existing memory and shared-lock rules.
