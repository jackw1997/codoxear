Independent hubs, local identities

This design supersedes the mandatory central account service in the earlier relay design. No Codoxear-operated account database, registry, gateway, subscription, or hosted service is required.

Ownership and authorization

Every hub and Computer has one person owner. Each Computer belongs to one hub. Hubs bind proven identities to hub-local people. A person can own or join several hubs; there is no global user ID. Owners invite other people. Creating an agent requires hub access and Computer operator access together, under the same verified hub-local person. Hub retention policy overrides Computer policy when defined.

A client may retain several authenticated methods for a hub-local person. The client considers the usable identities, combines accessible agents, and checks access before displaying a cached conversation. Permissions remain server decisions on every request. Identity tokens cannot be combined to invent ownership, or used across hubs. Matching email claims never automatically merge accounts. An existing identity attached to another local account cannot be reassigned by a login.

Login and local storage

  1. The user adds a hub URL. The hub advertises its own issuer and authentication capabilities.
  2. The client opens that hub's sign-in page with an exact registered callback and PKCE challenge. Passwords and provider login happen with that hub/provider.
  3. The hub validates the provider response and issues an expiring authorization code. The client verifies the callback source, origin and state, and redeems the code using its verifier.
  4. The client saves hub-scoped session credentials in its local credential collection. It sends a credential only to its issuing hub. Refresh tokens rotate; sessions and identity bindings are revocable.
  5. Only a hub's accepted proofs contribute access. An existing provider login is not automatically a token valid for a different hub/application.

The web client uses IndexedDB, with short-lived access credentials and rotating refresh credentials. It never stores passwords or provider secrets, and never puts bearer credentials in URLs. Browser storage is not an OS secure credential vault: trusted client-origin scripts, malicious extensions or a compromised browser profile can access it. The static client host remains a trusted software supplier even though it stores no user accounts. Native clients should use their platform credential store; native implementations must be tested separately.

Trust boundaries and security limits

Use separate hostnames for hubs operated by different people. Browser cookies are scoped to hostnames, not ports; separate ports on one hostname do not isolate mutually untrusted login servers. The demo uses one operator for all its ports. Every hub administrator is trusted with that hub's identities, permissions and relayed content. The relay is protected by TLS but is not end-to-end encrypted against its hub operator.

Revocation stops subsequent authorized access and removes cached previews on the next permission refresh. It cannot recall a downloaded file, screenshot or other copy. Refresh-token rotation and explicit issuer checking protect important boundaries; passing tests is not a complete security audit or production certification.

One webpage, direct hub connections

The original sidebar, New session dialog, theme engine and Settings dialog are reused. Hub/Computer placement appears in agent metadata and the New session placement field. “Hubs & computers” opens a secondary page with an expandable hub list. Each hub expands to its computers and an Add computer button. Add hub sits in the header; Add hub and Add computer open separate pages with Back navigation. Login and connection pages use the same theme engine, tokens and control treatment as HarmonyOS. Switching agents retains the page and shell.

A service worker inside the browser routes the existing UI's API, SSE and file requests to the selected independent hub, attaching the appropriate local credential. It is not a server-side gateway. The page URL remains on the static-client origin, while network requests go directly to the hubs. Each hub explicitly allows its chosen client origins and OAuth callbacks. Any HTTPS static host can serve the client; it has no API proxy or identity database. Browser trust/storage belongs to the chosen client origin.

Shared page structure

All connection pages share one panel: a 60px header, explicit Back control, 20px content inset, 44px controls and the existing theme tokens. Larger screens use a bounded 520px paper surface over the undimmed agent interface; phones use the full screen. Forms, detail rows, errors and actions use the same components for hubs, computers, pairing, invitations and access rules. Clay, Slate and Paper retain their light and dark palettes.

Login, sign-in methods, callback recovery and logout use the same centered 420px authentication layout and Codoxear mark. Signed-out users can reconnect directly. The original agent workspace, flat Settings dialog, file viewer and New session dialog keep their established layout and theme engine. Opening or closing connection pages preserves the mounted conversation.

The browser checks include the exact signed-out state, narrow phones, foldable-sized and short landscape viewports, all six theme/mode combinations, separate add pages and nested access flows. Existing tabs keep their loaded JavaScript until refreshed; HTML and login scripts revalidate on a new load.

Attach a Computer

Open Hubs & computers, expand a hub you own, then select Add computer. Name the computer and open its Pair computer page. It includes a downloadable source package, an installation guide, and a copyable attach command. Install Node.js 22.13+, sign in to Codex, Pi or Claude Code locally, attach, then run Computer start. The native TypeScript runtime runs directly inside Computer; no Python package or local HTTP server is required. The guide contains the exact commands and troubleshooting checks.

Pairing codes contain eight uppercase letters/digits (excluding I, O, 0 and 1) and expire after 15 minutes. They are single-use, stored only as hashes, and rate-limited at redemption. New code invalidates the previous one. Lowercase or a separator between the two groups of four is accepted. The long-lived Computer credential remains a separate high-entropy secret on the computer.

Computer attach accepts --hub and --code, then prompts for a local runtime address, workspace and hidden password. The advanced private JSON configuration remains supported. No inbound connection or port forwarding to the computer is required.

Authenticated runtime verification

On 4 October 2026, the deployed browser created and attached Authenticated Computer under Home demo. Both Codex · authenticated and Pi · authenticated used real ChatGPT OAuth credentials and gpt-6.1-sol inference, executed shell write/read operations, streamed their replies through the hub, and displayed their generated files in the browser. The checks ran in an isolated Docker Computer with verified TLS to the real provider; credentials stayed outside the repository and downloadable package.

The other demo Computers still use scripted model responses. The authenticated examples remain available in the same agent list. This verification covers the browser → hub → Computer → CLI path; it does not claim Claude or native mobile acceptance, or a complete production security review.

Deployment

npm run hub defaults to an independent hub. Its private config supplies origin, hubId, catalog, database, signingKey, otpKey, allowed clientOrigins and registered clients. First start requires bootstrap owner credentials. Hub-local provider and delivery configuration is optional. npm run client serves static files; it does not run an account service.

Migration exports each old hub into a separate database, preserving Computer bindings, owners, memberships, agents and retention state. Shared-authority sessions and transient credentials are not imported. Users sign in separately to each hub after migration. Existing agent processes must remain running during demo cutover. Old shared-authority mode remains explicitly marked legacy for existing deployments and regression tests.

Invitations and selective sharing — local implementation

Owners can now address invitations to email, a verified phone number, or an exact Feishu/WeChat/OIDC connection, subject and tenant. Provider and phone recipients do not need linked email. Computer owners can share one agent with an active hub member as Viewer or Operator independently of computer membership; direct revocation removes that agent’s explicit and historical grants. Creation and workspace permissions remain separate. Workflow and Docker/browser evidence. The running demo snapshot is unchanged; live provider gates remain open.

Release limits and No-Go reasons

Feature No-Go until Reason
Browser downloads larger than 256 MiB A cross-browser streaming download handoff is implemented and tested The original Download button currently buffers authenticated files in memory, capped at 256 MiB; files are not cached persistently.
Live Feishu / WeChat / Google login Hub operator registers applications/callbacks, supplies credentials, and completes provider-specific live acceptance tests Adapter and local identity checks cannot prove behavior with unconfigured production providers. Google uses the OIDC adapter.
Live email / SMS codes Hub operator configures and tests delivery No email/SMS vendor credentials or funded delivery account are supplied.
Claiming browser storage is a hardware credential vault Never claim this for the browser implementation Same-origin scripts can access web storage. Encryption with a key available to those same scripts does not remove that trust.
HarmonyOS / iOS / Android parity Native per-hub login collection, platform secure storage, callback handling and device tests are completed The browser implementation does not prove native lifecycle or keystore behavior; existing HarmonyOS work is preserved.
Safari / mobile browser production certification Real-device tests cover service workers, streaming, downloads, login popups and persistence Desktop Chromium and a mobile viewport do not prove platform behavior.
Remote logout while a hub is offline The hub can be reached to revoke the session Local disconnect can erase credentials immediately but cannot guarantee offline server revocation.
Automatic hub discovery / cloud identity sync Separately designed, optional, user-controlled discovery or export is implemented A mandatory global registry or account sync would contradict the accepted architecture.
Cross-hub Computer ownership transfer with live credentials A destination admission and source-detachment protocol is implemented across independent databases The old shared-database transfer command is not evidence of a cross-hub transfer protocol.
