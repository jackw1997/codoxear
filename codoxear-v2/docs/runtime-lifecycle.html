Codoxear OAR refactor design

Status: architecture agreed for implementation; not implemented or deployed. New managed sessions use OAR behind a thin Codoxear runtime interface on each Computer. Same-Hub cross-Computer delegation is in scope; cross-Hub delegation is deferred. Existing terminal sessions retain their supported native broker path. This accepted direction supersedes the earlier recommendation to implement a direct Codex driver first and leave OAR for later.

What Raft actually does

AgentProcessManager
  → ChildProcessRuntimeSession
  → CodexDriver
  → codex app-server --listen stdio://

The inspected Raft release starts an app-server child with pipes. It initializes the protocol, starts or resumes a thread, submits idle input with turn/start, and steers active work with turn/steer and an expected turn ID. It consumes structured events instead of typing commands into a tmux pane.

This is Raft's own driver. Its OAR dependency in this snapshot is used for runtime account-usage collection; it is not the live Codex control path. The manager tracks launch/process identity and keeps restart snapshots with the native session ID. That source inspection does not establish durable storage of every in-flight operation.

Accepted Codoxear boundary

Phone / browser ↔ Hub ↔ Computer supervisor
                                ├─ thin Codoxear runtime interface
                                │    ├─ OAR → Codex / Pi / Claude / supported runtimes
                                │    └─ native extensions for required adapter gaps
                                └─ existing terminal sessions: current broker

The Computer owns process lifetime and a private driver connection. The Hub retains account permissions and the stable agent catalog. The client renders events and submits authorized actions. Closing a phone tab or reconnecting to a Hub must not stop the underlying agent.

  • Persist the Codoxear agent ID separately from the native thread/session ID, launch generation, and process identity. A restarted process does not become a new user-visible agent.
  • Use explicit open/resume, submit, steer, interrupt, approval response, event subscription, and close operations. Keep interrupting a turn, suspending a runtime, archiving history, and deleting a session distinct.
  • Use one active owner for each native session. Preserve existing broker sessions; moving a running TUI session to a different driver requires an explicit, quiescent handoff.
  • Persist delivery receipts and event cursors on the Computer. A request acknowledged by the transport is not proof that the turn completed. Reconcile uncertain delivery after a crash before considering a retry.
  • On reconnect, restore the saved conversation context and reconcile state. The accepted recovery policy reruns an interrupted tool as a fresh attempt when retrying; it does not require restoring the tool process or continuing it at an instruction boundary. Preserve the interrupted attempt and give its replacement a new attempt identity. Let the native runtime issue the new call under the configured permissions; OAR does not provide a universal arbitrary-tool replay operation. An explicit user stop stays stopped until continuation is requested. A crash with no reliable result is outcome-unknown, rather than confirmed interruption: account for possible partial effects before retrying, and retain existing uncertain-delivery protections.
  • Route backend approval requests to the authorized client and settle the original RPC request. Preserve configured permission policy.
  • Keep private provider URL, key, model, workspace, and authentication configuration on the Computer. A driver change must preserve the user's LiteLLM/Kimi setup and isolate each session's configuration.

Codex exposes thread start/resume/read, turn start/steer/interrupt, streaming items, and approval requests through app-server. Use OAR's supported adapter operations and reuse existing native control work where an explicit extension is needed. Keep one runtime owner per session. The main Pi + Kimi agent can retain its existing runtime and gain a Codoxear delegation tool; it need not migrate before it can delegate.

OAR integration requirements

The separately inspected OAR snapshot provides useful examples of correlated RPC calls, early-event buffering, native session IDs, cooperative interruption, and bounded process cleanup. Its Pi SDK path needs a separate process for environment isolation. That snapshot requires Node 24, while Codoxear's current baseline is Node 22.13 or newer.

Both inspected projects use permissive defaults in parts of their managed execution paths. The inspected OAR Codex adapter records server requests without settling interactive approval requests; Raft rejects unsupported requests. Codoxear should implement the intended approval flow rather than inherit these policies implicitly.

Preserve configured permission/sandbox policy. Add a supported adapter extension for required approval replies; until that path is verified, refuse unsupported managed configurations clearly instead of silently broadening permissions. Preserve private provider URL/key/model and Pi's existing LiteLLM settings. Isolate Pi SDK worker configurations where process-global provider/environment state would collide. Required operations must pass actual native behavior before a new driver replaces an existing path.

Memory on the 8 GiB computer

Immediate cleanup is authorized but blocked. The user requested stopping all Codoxear demo/test containers created during this work, including copies resumed after the crash. The current execution restrictions deny access to the Docker socket. No containers have been stopped under this request, and no replacements are being launched. Keep container filesystems and host data directories until their histories and credentials are safely accounted for. Subsequent design reviews use read-only subagents without launching agent runtimes or containers.

The last available inventory contained seven preview/demo containers. The visible service cgroup records one OOM kill, but supplies neither a timestamp nor a victim; it does not prove which process caused the reported crash. Current process isolation prevents an accurate host-wide inventory.

Prepared verification changes serialize test files, add a shared per-user lock, and cap verification containers at 2 GiB, two CPUs and 512 processes. The container cap does not cap Docker image builds or the whole host. These changes have not been behaviorally verified or deployed because Docker is inaccessible.

  • Store conversations, native thread IDs and event history on disk. Start or resume a backend only when active work needs it.
  • Unload a runtime only after confirmed quiescence: no active turn, tools, subagents, pending approval or uncertain delivery. A phone disconnect alone is not that evidence.
  • Start with at least 2 GiB of host headroom as a proposed admission policy. Measure process-tree PSS or cgroup memory and tool descendants; do not estimate consumption from session count alone.
  • Bound simultaneous active runtimes, history/event buffers and restart retries. Under pressure, defer new launches and release safely idle runtimes before risking an OOM kill.
  • For managed Codex conversations, replace the current TUI plus PTY control path with direct app-server. Avoid adding a second runtime owner. Preserve terminal integration as a separate supported path.

OAR's inspected Codex adapter starts an app-server for each opened session. It supplies lifecycle operations, but memory savings depend on Codoxear's lazy-open and idle-dispose policy. Managed app-server sessions remove the interactive terminal layer; actual savings must be measured. Earlier estimates of six, eight or ten sessions under 2 GiB were hypothetical planning examples, not benchmarks or measured P99 capacity. The 2 GiB verification cap does not define the production session budget. Admission must account for resident idle workers and descendant tools as well as active turns.

Subagents on another Computer in the same Hub

Current scope: an agent on Computer A can request a subagent on Computer B within the same Hub. Cross-Hub subagent delegation is explicitly deferred to later versions. This records the accepted design; the distributed path is not implemented or deployed yet.

Parent → Computer A → shared Hub → Computer B → OAR/native runtime → Child

The tool selects a target Computer within the initiating Hub, alongside runtime, model, workspace and task. The Hub derives the source identity from authenticated delegation context, not a caller-supplied Hub ID. The initiating Hub-local principal and parent agent's delegated authority must permit creation on the target Computer. Sharing a parent agent or belonging to the same Hub does not grant access to every Computer. The destination owns execution and enforces resource admission and local workspace/runtime policy.

Reject a cross-Hub target as unsupported in this version. Do not add Hub federation or cross-Hub delegation grants in this iteration. Existing multi-Hub client access and Computer transfer remain separate capabilities. Both Computers retain their current Hub binding. Runtime provider credentials stay on the destination Computer.

Record parent/child references using Hub and Computer identities, durable request IDs and launch receipts. A timeout after remote acceptance must resolve the existing receipt instead of spawning a duplicate child. Keep native session ancestry distinct from Codoxear's cross-Computer parentage. Events, result access, follow-ups and cancellation are scoped to the child and remain subject to destination authorization. Task context/artifacts require explicit transfer; local paths are not shared filesystems and file/Git grants remain separate.

OAR runs at the destination and manages the selected local runtime. Codoxear owns routing, grants, parent/child records, result delivery and recovery. Browser or link loss is not a confirmed cancellation. The accepted interrupted-tool rerun policy does not remove the remote launch deduplication requirement.

Delegation tools, versions and persistence

Expose a consistent Codoxear tool vocabulary for discovery, spawn, send, wait, list, interrupt and close. Route local and same-Hub remote targets through the same authority and receipt boundary. A Pi extension or MCP bridge connects the main agent to a Computer-owned controller. Bare OAR MCP is not the distributed controller: its local crew is tied to its client lifetime. Parent/viewer disconnects alone must not close remote children.

Computers exchange the versioned Codoxear protocol, not OAR objects. Pin one tested OAR package and dependency lockfile in the initial Computer release, and provide its required Node version on the Computer. No shared OAR process or synchronized OAR memory is required. Advertise supported protocol versions, runtime versions and capabilities; reject unsupported combinations. Mixed OAR versions can be considered later through that protocol boundary.

Persist Codoxear agent and parent identities, delegation request/launch receipts, native session IDs, execution/stream generations, OAR/runtime versions and terminal results. OAR's in-memory cursor is not durable history. Child results and permitted artifacts return through the Hub; workspace paths refer to destination-local files. Let the existing main agent choose from configured runtime/model combinations, without claiming OAR selects the best combination automatically.

Depth and resource budgets apply across same-Hub delegation chains. Enforce them through authenticated lineage and destination admission; independent OAR per-process limits are insufficient. Automatic task scheduling from conversation metadata is still out of scope. DSH/ZCode remain adapter-extension candidates, not claims of built-in or accepted runtime support.

Upgrades are staged against tested Computer/OAR/runtime combinations. Preserve existing sessions, native history and catalog identities. Verify launch, stream, tools, controls, exit and native resume before selecting a newer runtime for new executions. A runtime updater reporting success is not a compatibility test, and a downgrade does not guarantee older code can read newer native history.

The missing old sessions are a separate catalog issue

The trusted-endpoint cutover kept the old processes running but directed default sign-in and catalog requests to a fresh Hub database. Read-only inspection found 19 original agent records across two existing Hubs, plus two agent records in the new native catalog at the recovery baseline.

A prepared router change restores the original Hubs as the default and explicitly routes both sets of Computer IDs and signing-key hints. Browser refresh and revoke requests carry their existing access-token routing hint, while each Hub still authenticates the actual operation. This preserves separate authorities without copying credentials or merging account databases.

Recovery is not deployed. The router subagent reported six passing Docker checks before the environment changed. The browser baseline was captured, and the pending changes pass static TypeScript checking. The current execution environment denies access to the Docker socket, so production build, final browser recovery, and deployment remain outstanding. The saved public gateway still has its prior default-new configuration.

A normal application update must preserve the existing Hub databases, keys, identities, and catalog IDs. Demo reseeding must be explicit. Any switch must verify that original sessions remain visible and that newer sessions remain accessible after authentication refresh.

Acceptance before enabling the refactor

  1. Finish catalog restoration and verify original and newer sessions together in the real browser.
  2. Exercise one opt-in Codex managed session through actual app-server: create, stream, steer, approve/reject, interrupt, read history, stop, and resume.
  3. Kill only a disposable Docker fixture worker at submission boundaries; verify durable identity, uncertain-delivery handling, and absence of duplicate execution.
  4. Confirm configured provider URL/key/model, sandbox policy, queued input, tool results, and browser reconnect behavior.
  5. Compare Pi and Claude driver parity before enabling their managed paths. Keep terminal handoff available throughout.
  6. Use two isolated Computers in one Hub to verify target authorization, local/remote tool parity, cross-Hub rejection, durable launch deduplication after lost acknowledgments, result/follow-up/cancel delivery, parent restart and destination disconnect.
  7. Measure whole-process-tree or cgroup memory with resident idle children, simultaneous work, large histories and descendant tools. Verify admission, buffer bounds, safe idle cleanup and delegation depth across Computers.
  8. Exercise version/capability mismatch and an isolated runtime upgrade with native resume; preserve the previous catalog and configuration.
