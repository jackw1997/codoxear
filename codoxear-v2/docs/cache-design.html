Architecture update: Independent hubs and local identities supersedes the mandatory central account service and browser gateway described below.

Agent switching and local storage

The browser keeps one original Codoxear workspace mounted. Agents have global IDs in that workspace. A TypeScript browser gateway on the account origin translates each request to the agent’s owning hub and computer. Switching existing agents changes the conversation without changing the browser origin or opening another sign-in page.

The gateway obtains a hub-specific grant from the identity authority. The browser never receives that bearer credential. Hub registration determines the target origin; clients cannot supply arbitrary upstream URLs. Each owning hub continues to enforce agent access, workspace file grants, and hub/computer retention policies. Computer connections remain outbound, including from private IP networks.

Access and lifecycle

Every selection, including hash navigation, checks current access before using a cached preview. Only the selected agent has a live transcript connection. Switching cancels the previous stream and pending message requests; generation checks reject stale results. A five-second directory refresh drops inaccessible preview entries and invalidates entries whose access mode changes. Server checks are authoritative; cached data never enables a send or file operation.

Logout and failed authentication clear account content from the active workspace. Storage is scoped to account and login session, so a later login cannot restore the previous account’s drafts. Offline or closed browsers cannot receive immediate revocation; the next authenticated interaction rechecks access.

One browser origin

Sign-in, the agent directory, conversation traffic, agent creation on any authorized computer, file transfers, account settings and agent settings all use https://codoxear.gzeek.com:8445/. Hub ports remain service endpoints for Computers and the server-side gateway. Browser navigation and browser API calls do not target those ports. Creating and switching agents preserve the mounted workspace. Settings pages intentionally display their own screen on the same origin.

The web gateway checks the current account session and obtains a target-hub grant on the server. Target URLs come only from registered hub records. Native clients keep their existing scoped protocol. The web/identity process can be deployed separately from the hub and Computer processes, preserving running agents during a web update.

The demo uses real Pi processes, files, and tool execution with scripted model replies. Restarting its isolated container ends those CLI processes; persisted conversations remain on disk. The full product’s existing No-Go register still applies.
