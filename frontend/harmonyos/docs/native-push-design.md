# Native push delivery contract

Background notifications use HarmonyOS PushKit alert messages, independently of Web Push subscriptions. The existing final-response/intercom announcement boundary remains authoritative. Registration means only that the authenticated server stored a current device token; provider acceptance is not proof of delivery. Device offline/terminated delivery needs a signed, entitled app and a real device.

One installation has one random registration ID per server. Token rotation replaces that record atomically. Disable first removes the server registration and then revokes the native token. Either confirmed server removal or confirmed provider token deletion is sufficient to stop future delivery; failure of both remains an error with retryable local state. A request already in flight may still deliver. Logout attempts token revocation even if the old server cannot be reached. Native local polling must stop when provider registration succeeds to avoid duplicate alerts. App termination must not revoke an enabled registration. Account/server change must not silently reuse an old subscription. Network failures must preserve retryable state and never display a false success.

No service-account key or JWT goes to the app. Server configuration is an operator-owned service-account JSON path. Only authenticated registration endpoints accept tokens; status responses never return tokens or credentials. Sending uses the fixed Huawei HTTPS host, PS256 JWT, v3 project URL, alert push-type 0, 300-second offline TTL and explicit WORK classification (requires Huawei classification entitlement). Debug/test-message mode is explicit.

Sources consulted: Huawei [request parameters](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/push-scenariozed-api-request-param), [request examples](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/push-scenariozed-api-request-example), [official server sample](https://gitee.com/harmonyos_samples/push-kit_-sample-code_-server-demo_-java), [v3 requirement](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/push-faq-1). Local installed PushKit declarations provide the client API signatures.

## Implementation and provisioning

The client uses PushKit `getToken`, `deleteToken` and `tokenUpdate`. It requests notification permission only after explicit opt-in; foreground-only opt-in also survives application restart. Missing server support/configuration or unavailable unsigned-app PushKit registration produces an explicit “App running only” status. The status does not claim background delivery. A failed registration retains its token for cancellation, including after a lost HTTP acknowledgement or process restart.

On the server, set `CODEX_WEB_HARMONY_PUSH_ACCOUNT` to a private Huawei service-account JSON file containing `project_id`, `key_id`, `private_key`, `sub_account` and `token_uri`. Keep it outside the checkout. `CODEX_WEB_HARMONY_PUSH_TEST=1` explicitly requests provider test messages. The matching application must have PushKit enabled, a valid signing profile and WORK classification entitlement. No project identifier, key or entitlement was invented for this implementation.

Authenticated GET `/api/notifications/harmony` returns configuration availability; POST accepts `device_id`, `token`, `server` (canonical `/api/me` URL) and boolean `enabled`. Registration files are written atomically with mode 0600. Rotated tokens replace the stable installation record; stale disable requests cannot delete a newer token. Provider error 80300007 removes the invalid token. HTTP 200 alone is not success: the accepted business code is 80000000. Provider response text is not exposed because it may contain tokens. Redirects are rejected to keep the signing bearer at the documented provider host.

Verification distinguishes three layers: actual ArkTS ownership/race tests with platform mocks; real authenticated HTTP and emulator settings/click interaction; and provider/device delivery. The first two do not prove the third. There is no Huawei service-account credential or signed physical device in the current test environment. Background/offline/process-terminated delivery, WORK entitlement, production provider acceptance, OS notification permission changes and the physical-device foreground/background behavior remain acceptance work.
